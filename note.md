# Slipstream — Project Notes

## What it is
Slipstream is an open-source smart order execution engine. Instead of sending one large market order, it slices the order over time (TWAP) and checks every slice against hard risk limits. It then measures slippage against what a single market order would have cost at arrival. v1 paper-trades BTC/USD against Kraken's live public order book.

## The real-world problem
Large orders move the price against the trader (market impact). Institutions pay for execution algorithms and smart order routers to reduce this cost. Retail traders and small funds usually send one market order and absorb the slippage. Slipstream brings the same tools into the open, where they can be audited and measured.

## Architecture
    Kraken WS (public)   -+
                          +-> Python orchestrator --gRPC (loopback)--> C++ engine
    Coinbase WS (public) -+   parse + validate                           one book per venue
                              drive clock                                schedules (TWAP/VWAP/POV/AC)
                              JSON logs + summary                        smart router (price + fee)
                                                                         risk checks -> simulated fills

- The engine is deterministic. The caller supplies `now_ns`, so live runs, replays, and tests share one code path.
- Risk checks live in C++ and run before every fill. Live mode, when added later, must pass the same gate.

## Key decisions
| Decision | Why |
|---|---|
| Two services over gRPC | Clean contract (`execution.proto`), independent testing, C++ hot path + Python glue, the same split used on real trading desks |
| Caller-supplied clock | Deterministic tests and replays with no hidden time dependency |
| Paper mode only in v1 | Prove correctness before any real money is at risk |
| Kraken public WebSocket v2 | Free, no API key, well documented |
| WSL2 Ubuntu 24.04 + venv (no Docker) | Matches CI's native `ubuntu-24.04` runners exactly; Docker Desktop was an extra moving part that added no environment fidelity a native WSL2 install didn't already give |
| Hash-pinned Python deps | Supply-chain protection |
| Loopback-only gRPC | No network exposure without TLS and auth |
| Route by all-in price (price + taker fee) inside the C++ engine | Fees often exceed slippage on crypto venues; routing inside the engine keeps one deterministic risk gate over the total position |
| Fees configured once on the engine; Python reads them back from `GetStatus` | Two fee configs would drift; the CLI refuses to run when `--venues` differs from the engine's venues |
| Coinbase parser mirrors the full book and sends a top-N view | Coinbase sends full-book deltas but the engine keeps only N levels, so deleted top levels could never be refilled |
| Exchange trading rules fetched at startup and passed as engine flags | Always current, with no keys. The engine stays the single source of truth, and it never makes network calls |
| Slices wait for the cheapest exchange's minimum; the risk check uses the routed cost including fees | A small slice sent to a pricier exchange cost 20 bps more in a live run, and checking at the mid let book-walking and fees exceed the limit |
| Heartbeats keep a quiet exchange fresh | A healthy Kraken book can stay unchanged for more than 2 s, and marking it stale pushed fills to the more expensive exchange |
| Cross between venues is allowed within fees; a cross that survives fees, or a venue whose own book is crossed, skips the step | Live venues sit crossed by ~0.15 bps all day because fees make it unprofitable; only a post-fee arbitrage or a self-crossed book signals bad data |
| Single-writer engine loop: one thread owns all books, orders and risk state; unary calls (Submit, GetStatus) go through a command queue drained ahead of market data | Removes the global mutex from the hot path without giving up one consistent snapshot per step; order entry never waits behind a burst of market data |
| One `MarketStream` per venue in, one `Subscribe` stream out, instead of per-message unary calls | A long-lived stream removes the per-message round trip (5-10x less overhead) while keeping the engine a separate, crash-isolated service, which is the shape multi-user needs later |
| `--clock live` (engine's own clock, client time ignored) vs `--clock replay` (recorded `recv_ns` drives the clock, no timer) | Live time can't be spoofed by a client; replay stays exact and runs as fast as the CPU allows, so tests and the benchmark are reproducible |
| One OS process per venue feed (`multiprocessing`, spawn) | Python runs one thread at a time per process; a 5 MB Coinbase snapshot parsing on the same loop as Kraken would delay Kraken's prices |
| Append-only results database, with `UPDATE`/`DELETE` triggers on every table and one allowed `runs` transition (`started` -> a terminal status, comparing every other column with `IS`) | The hourly evidence has to be trustworthy on its own; a table anyone (including a future bug) could quietly edit would undermine that, so the database enforces it at the SQLite level, not just in application code |
| One engine process and one gRPC connection shared across both sizes in an hourly run, rather than a fresh engine per size | Building and starting the release engine takes real time; sharing it keeps the whole hour (two sizes x four algorithms x 10 minutes) comfortably inside the hour |
| Bounded retry (5 attempts, 100ms apart) on the engine's "another subscriber is active" rejection when the second size opens its `Subscribe` stream | Closing the first size's stream and the engine noticing the cancellation (it polls every 50ms) race on a shared connection; retrying a few times costs at most half a second and turns a timing gap into nothing, instead of failing a run over it |
| Nightly Hypothesis profile uses a random seed and 2000 examples, vs. CI's derandomized 200-example profile | A fixed seed reproduces the same 200 cases on every PR, which keeps PRs fast and deterministic but can never find a case outside those 200; a random seed nightly explores new inputs each run, and `print_blob=True` makes any failure it finds reproducible |
| Hard disk cap (`SLIPSTREAM_RECORDINGS_MAX_MB`, oldest-first eviction down to 90% of the cap) on top of the time-based retention tiers | Time-based thinning and expiry bound growth eventually, but not the next few days if collection volume rises; a hard cap with 90% headroom stops the collector from immediately hitting the cap again next hour |
| xz rejected for recording compression, gzip-9 kept | Measured on live Kraken+Coinbase BTC/USD data, xz saved only ~12% over gzip-9 — short of the 30% bar that would have justified its extra CPU cost and a second compression code path |

## Known limitations (v1)
- Paper fills do not consume book liquidity. Each fill assumes the displayed book is still there at the next step.
- Prices and quantities are `double`. Fixed-point decimals are planned before any live trading.
- Kraken book checksums are verified (live, while recording, and in replay): each connection mirrors the book at its subscribed depth in exact decimals, recomputes Kraken's CRC32 over the top 10 asks and bids after every message, and on a mismatch the feed stops and the run fails. There is no automatic resync yet; recovering a desynchronised book is part of the reconnect work. Coinbase publishes no book checksum.
- Phase 2 (PRs #16, #18, and this cleanup PR) replaced the per-message unary calls with one concurrent market stream per venue and a single-writer engine loop; see the dev log below and the README's Performance section for measured numbers.
- The repository lives in a OneDrive folder. OneDrive locks files under `.git/worktrees` and slows writes, which is the likely cause of the old recording gap. Moving the repo outside OneDrive is recommended.
- The slippage comparison includes market drift during the execution window. It illustrates one run; it does not prove an edge statistically.
- If one of several orders submitted together is rejected by the engine, the orders accepted before it keep working in that engine process; the CLI exits with an error. The demo scripts start a fresh engine per run and stop it on exit. A cancel RPC is planned.

### 2026-09-24 — Week 2: execution schedules

- Engine: one `Schedule` interface with TWAP, VWAP (normalized volume weights), POV (share of live volume, halts at the deadline), and Almgren-Chriss. Kraken's best level holds far more than a slice, so the measured impact was zero and calibration refused to run. The fail-safe worked, and no order was submitted. It was replaced with the depth-curve fit and a regression test built from a realistic deep book.
- Security review fix: the OHLC client refuses HTTP redirects, because urllib would otherwise follow an https-to-http downgrade.
- Four-algorithm end-to-end test against the real engine: every fill matches a hand derivation, including VWAP weights across a 15-minute bucket boundary, POV volume timing, and Almgren-Chriss at κτ = 0.5.
- First live comparison (20 min, 0.005 BTC): POV −1.77 bps, Almgren-Chriss −0.47, VWAP +8.31, TWAP +8.89. BTC drifted up during the window, which rewarded the schedules that traded early. ### 2026-09-25 — Week 2: smart routing across venues (PRs #10–#13)

- **Cleanup (this PR).** Removed the now-unused `ApplyBookUpdate`, `ApplyTrades` and `Step` RPCs (field numbers and names reserved), and the sync `EngineClient` and the runner's old hot path. Added `bench/pipeline_bench.py` and `scripts/bench_pipeline.sh`: a deterministic 50k-event synthetic replay stream (seeded RNG, alternating venues, trades every 20th event driving a 0.5-participation POV buy) measuring client send-to-fill latency and reading the engine's own `stats`. Wired into `scripts/ci.sh` after the Python tests.
- Bug found while building the benchmark: sending all 50,000 events back-to-back with only `await asyncio.sleep(0)` between them filled `MarketStreamWriter`'s internal 1,000-item queue almost immediately (measured `qsize()` pinned at 1,000) and stayed there, because Python's single-threaded event loop can't drain a queue faster than it's fed without an explicit yield that lets the pump task actually finish a write. That inflated measured p50 to ~93 ms — a client-side backlog, not pipeline latency (the engine's own `stats` still read ~33 µs). Fix: pace each send to wait until the local queue is empty again before enqueuing the next event, which dropped p50 to ~300-400 µs and matched the engine's own histogram once the client-side wait was removed from the critical path.
- Measured (local, `bash scripts/bench_pipeline.sh`, committed baseline in `bench/baseline.json`): 50,000 events, 2,500 fills sampled; client send-to-fill p50 340 µs, p99 0.93 ms, p99.9 3.0 ms; engine-side (ingest-to-processed, from `stats`) p50 33 µs, p99 131 µs. A first version reported p99 6.6 ms and p99.9 35 ms; review found the pacing treated "dequeued" as "sent" and recorded send times after the fill could already arrive, so `MarketStreamWriter.drain()` now waits for the write itself and the send time is recorded before waiting. The engine meets the 150 µs design target; the end-to-end client figure does not, because of Python asyncio and gRPC overhead. Both client p99/p99.9 vary noticeably run to run (observed 300 µs-650 µs p50, up to ~2x) from ordinary Python scheduler and GC jitter, which is why the CI gate uses a 2x (local) / 3x (CI, via `SLIPSTREAM_BENCH_TOLERANCE`) tolerance on p50 rather than an absolute threshold.
- Full `bash scripts/ci.sh` (codegen, ASan+UBSan build and tests, TSan build and stream/loop/queue tests, Python lint/types/tests, bench lint/types, the benchmark, pip-audit) passes end to end: `CI OK`.

### 2026-09-27 — PR A: hourly collector and results database
- `python/slipstream/db/`: an append-only SQLite `ResultsDB` (WAL, `foreign_keys=ON`, a 5s busy timeout). Migrations are `*.sql` files loaded through `importlib.resources`, so they work from a plain repo checkout with no packaging step. Every table blocks `UPDATE`/`DELETE` with `BEFORE` triggers that `RAISE(ABORT, 'append-only')`, except one trigger on `runs` that allows exactly one `started` -> `completed`/`failed`/`abandoned` transition (its `WHEN` clause compares every other column with `IS`, so a second finish, or changing `side` alongside the finish, is refused the same way).
- Recordings needed their own append-only `recordings`/`recording_deletions` tables, since `runs` itself cannot be edited after the fact: thinning a raw recording deletes the file but keeps the `recordings` row (with its SHA-256) and adds a `recording_deletions` row, so the fact that it existed stays auditable.
- `python/slipstream/collect.py`: `run_hour` opens one engine connection for the whole hour, fetches venue fees, venue trading rules and Kraken OHLC calibration once, then runs each configured size (0.01 and 0.25 BTC) one after another — buy on even UTC hours, sell on odd — recording raw market data (gzip) concurrently with a `LiveSession` over all four algorithms. A run that fails is recorded `failed` with its error and the next size still runs; a DB failure is the only thing allowed to raise out of an hour's collection.
- Found while testing against a real engine: order ids like `h2026092710-0.01-twap` were rejected — the engine only allows alphanumerics, `-` and `_` in an order id, and the qty's decimal point isn't one of them. Fixed by encoding the qty with `p` for the point (`0p01`), used in both order ids and recording file names.
- Found the same way: running both sizes back-to-back against one shared engine connection intermittently hit `FAILED_PRECONDITION: another subscriber is active` on the second size's `Subscribe` call. The engine polls for a cancelled stream's cleanup every 50ms (`service.h`'s `kSubscribePoll`), so closing the first size's stream and the engine noticing it race. Fixed with a bounded retry (5 attempts, 100ms apart) in `collect.py`, scoped to that one error message, rather than touching the engine's or `session.py`'s teardown.
- `scripts/collect_hourly.sh` builds the release engine, starts it on `127.0.0.1:0`, reads its bound port from stdout the same way `conftest.py`'s test fixtures do, runs the collector against it, and stops it via a trap on exit. `scripts/install_task.ps1` registers or removes the Windows scheduled task (hourly at :05, current user, logged-on only, no stored password, standard privileges, `IgnoreNew`, a 50-minute time limit); it never runs `-Install` itself, and neither did this session — that is the user's call once the PR is merged.
- `bash scripts/ci.sh` passes end to end: `CI OK`.

### 2026-09-27 — PR B: research site and publishing
- `python/slipstream/site/stats.py`: `median_ci`/`diff_ci` bootstrap a 95%-style interval (1,000 resamples, fixed seed) for a sample's median and for the difference of two medians; `verdict()` only names a cheaper side when that interval excludes 0, and always reports `n` otherwise. A bare `except Exception` at the top of `publish()` guarantees a failure there can never propagate into the hourly collector — it only ever logs and returns nonzero.

- **Disk budget (`feat/storage-budget`, PR #26).** New `python/slipstream/storage.py` holds `StoragePolicy` (7-day full retention, thinned to the 12:00 UTC hour through day 90, deleted after; a hard cap via `SLIPSTREAM_RECORDINGS_MAX_MB`, default 1024 MB, validated at startup; daily gzip'd backups, 7 kept; logs pruned after 14 days) and the housekeeping functions `collect.py`'s `_housekeeping` wires together once an hour, after the live runs finish and the process has lowered its own niceness: `daily_backup`, then (once a day, at hour 0 UTC) `db.thin_recordings` / `expire_recordings` / `prune_old_logs`, then `enforce_recordings_budget` (oldest-first eviction to 90% of the cap, protecting the current hour's own recordings), finishing with a `disk_usage` log line every hour.
- Recompressing recordings to xz was evaluated and dropped: measured on live Kraken+Coinbase BTC/USD data, xz saved only ~12% over gzip-9, short of the 30% bar that would have justified the extra CPU and a second compression path.
- `scripts/collect_hourly.sh` now skips the release engine rebuild when the binary is already newer than every `engine`/`proto` source file, and when a build is needed runs it `nice -n 19` plus `ionice -c3` (idle I/O class) so it never competes with the live engine or the collector, which both stay at normal priority — keeping the latency numbers the collector measures each hour honest.
- **Coverage (`chore/coverage`, PR #27).** `scripts/coverage.sh` builds a separate `build/coverage` tree with the `SLIPSTREAM_COVERAGE` CMake option (gcov, no sanitizers), runs ctest and `pytest --cov`, and writes text and HTML reports with gcovr and pytest-cov under `build/coverage-report/`. A `coverage` job in `ci.yml` puts both summaries in the job summary and uploads the HTML. Report only, with no threshold gate: a gate rewards tests that move the number rather than tests that catch bugs. First numbers: C++ 97.0% lines, 65.7% branches (gcov counts the compiler's exception-path branches); Python 92%.
- **Kraken book checksum verification (`feat/kraken-checksum`).** Every Kraken v2 `book` message carries a CRC32 of its top 10 asks (low to high) then top 10 bids (high to low), each price and qty written without the decimal point and leading zeros. Messages are now decoded with `parse_float=Decimal` so the checksum covers the exact wire text; each connection keeps a Decimal mirror at the subscribed depth (`kraken_checksum.KrakenBook`), truncated after every message because Kraken sends no delete for levels pushed out of scope. A mismatch, a missing checksum or an update before the snapshot stops the feed and fails the run, naming the venue and symbol. The recorder checks while recording; `replay` re-checks from the recorded subscribe ack on. Verified against Kraken's documented example and about 7,600 live BTC/USD messages at depths 10 and 100. No separate precision source is needed: the wire numbers already carry full precision.
- **Scheduled task runs hidden and installs disabled (`fix/hidden-task`).** The first real start of the task opened a console window and ended with `0xC000013A` (terminated as if by Ctrl+C, consistent with the window being closed) before the collector wrote anything. The task now launches through `conhost.exe --headless wsl.exe ...`, so no window opens (verified with a harmless command). `-Install` registers the task disabled, and new `-Enable` / `-Disable` switches start and stop the schedule, so installing and starting collection are separate decisions.
- **Feed reconnect (`feat/feed-reconnect`, sub-project 2).** On a network failure, idle timeout or Kraken checksum mismatch, the feed sends the engine an empty snapshot for its venue (so the engine never trades a pre-disconnect book, which also covers single-venue runs), then reconnects with jittered backoff (0.5 s doubling to 8 s, at most 5 per venue per run) and a fresh parser, so no update applies before the new snapshot. Other parser and engine errors still end the run at once. A checksum mismatch is retried because Kraken's documented recovery is a fresh snapshot; it is counted and capped like any other failure. `LiveSession` stops the run if no venue has a fresh book for 30 s. Recordings carry `kind: reconnect` marker lines; replay empties that venue's book until its next snapshot, and old recordings replay unchanged. Migration 002 adds the append-only `feed_reconnects` table (feed and recorder reconnects per run). Today, with every venue stale, the engine keeps orders working until their deadline and then catches up in one slice; an engine-side 30 s halt is the follow-up.
